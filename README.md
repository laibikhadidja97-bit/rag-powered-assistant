# RAG-Powered Assistant

Ask questions about a folder of documents and get answers that are **grounded in
those documents and cite the page they came from**.

The pipeline is the classic one — **embed → store → retrieve → generate** — written
out explicitly rather than hidden behind a framework, so every stage is a file you
can read and change. It runs entirely on a laptop: no API key, no server, no
account. LangChain is deliberately not used; the whole retrieval layer is about 250
lines and being able to see it is the point of the exercise.

The demo corpus is ten foundational machine-learning papers (Transformer, BERT,
GPT-3, ResNet, Adam, BatchNorm, ViT, LoRA, RAG, InstructGPT) — 279 pages, indexed
as 1,827 chunks. Point `--docs` at your own folder of PDFs, notes or `.txt` files
and nothing else changes.

```
$ python ask.py --show-only "What is multi-head attention and why is it used instead of a single head?"

[1] attention-is-all-you-need.pdf p.5  similarity 0.762
    output values. These are concatenated and once again projected, resulting in the

    jointly attend to information from different representation subspaces at different
    positions. With a single attention head, averaging inhibits this. ...

[2] attention-is-all-you-need.pdf p.4  similarity 0.702
    Scaled Dot-Product Attention Multi-Head Attention Figure 2: (left) Scaled Dot-Product

```

Drop `--show-only` and those passages are handed to the language model, which answers
from them and cites them by number:

```
$ python ask.py "What is multi-head attention and why is it used instead of a single head?"

<answer citing [1], [2] ...>

Sources:
 *[1] attention-is-all-you-need.pdf p.5  (similarity 0.762)
 *[2] attention-is-all-you-need.pdf p.4  (similarity 0.702)
  [3] vision-transformer.pdf p.13        (similarity 0.681)
 * = cited in the answer above
```

Worked end-to-end examples with the model's actual answers are in
**[sample_questions.md](sample_questions.md)**, regenerated by `python transcript.py`.

## Quick start

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

python get_data.py     # download the 10-paper demo corpus (~19 MB)
python ingest.py       # load -> chunk -> embed -> store   (~2 min on an M3)
python ask.py "What are the two pre-training objectives used by BERT?"
```

First run downloads two models from Hugging Face: the embedding model (~130 MB) and
the generation model (~3 GB). Both are cached afterwards.

For the web UI:

```bash
python app.py          # http://127.0.0.1:7860
```

## Using your own documents

```bash
python ingest.py --docs ~/Documents/course-notes --rebuild
python ask.py "What are the main ideas in chapter 3?"
```

`.pdf`, `.txt` and `.md` are supported. Ingestion is incremental — chunk ids are
derived from filename, page and position, so adding a file and re-running updates
the store in place instead of duplicating it. Use `--rebuild` after changing the
chunk size or embedding model, since old vectors are not comparable to new ones.

## How it works

```
data/docs/*.pdf
      │
      │  loaders.py      PyMuPDF, one record per page, whitespace repaired
      ▼
   pages  (279)
      │
      │  chunking.py     recursive split on paragraph → sentence → word
      ▼                  1200 chars, 200 overlap
  chunks  (1,827)
      │
      │  embeddings.py   BAAI/bge-small-en-v1.5 → 384-d unit vectors
      ▼
 vectors  (1827 × 384)
      │
      │  store.py        ChromaDB, persisted to data/chroma/
      ▼
 ┌─────────────────────────────────────────────────────────┐
 │  question → embed → cosine search → top-k chunks         │  pipeline.py
 │                                        │                 │
 │                                        ▼                 │
 │                    numbered context + question → LLM     │  generate.py
 │                                        │                 │
 │                                        ▼                 │
 │                          answer with [n] citations       │
 └─────────────────────────────────────────────────────────┘
```

### The decisions that actually matter

**Chunk size (1200 chars, 200 overlap).** This is the main retrieval knob. Too
small and a chunk loses the context that makes it interpretable; too large and its
embedding averages several topics together, so it matches everything weakly and
nothing strongly. 1200 characters is roughly 250 tokens — comfortably inside the
embedding model's 512-token window — and the 200-character overlap means a fact
that straddles a boundary still lands whole in one chunk. The splitter is
recursive: it breaks on the largest natural boundary that fits (paragraph, then
sentence, then word), so chunks rarely start mid-sentence.

**Pages as the unit of loading.** Documents are read one page at a time rather than
concatenated, which is what lets an answer say *bert.pdf p.4* instead of just
*bert.pdf*. A citation you cannot look up is not much of a citation.

**Asymmetric embedding.** BGE models are trained so that passages are embedded bare
but queries need an instruction prefix (`"Represent this sentence for searching
relevant passages: "`). Skipping it costs real recall and fails silently — nothing
errors, the results just get quietly worse. `embeddings.py` applies it, so the
caller cannot forget.

**Chroma over FAISS.** FAISS is faster, but it stores only vectors: you must keep
your own sidecar mapping row → chunk text and metadata, and that mapping is an easy
thing to let drift out of sync. Chroma keeps vectors, text and metadata in one
persisted collection. At 1,827 chunks the speed difference is irrelevant — 59 ms
per query.

**Over-fetch, then cap per document.** The store is queried for `4k` candidates and
trimmed to `k` with at most 3 from any one document. Without this, a question whose
wording happens to match one paper's phrasing fills every slot from that paper, and
a comparison question never sees the second half of its own answer. The candidates
were already retrieved, so this costs nothing. It is measurable — *"How do BERT and
GPT-3 differ in the way they are pre-trained?"* returns:

```
[1] bert.pdf p.14                 similarity 0.804
[2] bert.pdf p.14                 similarity 0.785
[3] gpt3-few-shot-learners.pdf p.18   similarity 0.765
[4] bert.pdf p.14                 similarity 0.764   <- cap reached for bert.pdf
[5] gpt3-few-shot-learners.pdf p.14   similarity 0.759
```

BERT's passages score higher on every slot, so an uncapped top-5 would have been
five BERT chunks and the model could only have answered half the question.

**A prompt that is allowed to say no.** The system prompt forbids outside
knowledge, requires inline `[n]` citations, and specifies an exact refusal string
for questions the passages do not answer. Greedy decoding (`temperature=0`) keeps
answers reproducible. `Answer.cited()` then parses the citations back out, so both
the CLI and the UI can flag an answer that asserts things while citing nothing —
the signature of a model falling back on its own memory.

## Does it work?

Retrieval and generation fail differently, and retrieval failures are the ones that
matter: if the right passage never reaches the prompt, no model can recover it. So
`evaluate.py` scores the retrieval half on its own against 12 hand-labelled
questions, each tagged with the document that genuinely answers it.

```bash
python evaluate.py              # retrieval only — no LLM, a few seconds
python evaluate.py --generate   # also checks answers stay grounded
```

| metric | result |
|---|---|
| hit@1 | 10/12 — 83.3% |
| hit@3 | 12/12 — **100%** |
| hit@5 | 12/12 — 100% |
| MRR | 0.917 |
| median retrieval latency | 59 ms |

The two questions that miss at rank 1 still land at rank 2, and both are cases
where another paper legitimately discusses the topic — ViT quotes the Transformer's
attention formulation, and several papers cite GPT-3's parameter count. With k = 5
the correct document is always in the prompt.

The `--generate` pass adds two grounding checks: in-scope answers must cite at
least one passage, and two deliberately out-of-scope questions (last Friday's Nvidia
share price, an amoxicillin dose) must trigger the refusal instead of an invented
answer.

### Where it breaks

Retrieval is the strong half; the 1.5B default generator is the weak one, and the
sample transcript shows it rather than hiding it. Asked *"How do BERT and GPT-3
differ in the way they are pre-trained?"*, retrieval did its job — three BERT
passages and two GPT-3 passages, exactly the right evidence — and the model then
misread them, inverting a claim about sentence separators and inventing a corpus
size for GPT-3 that appears nowhere in the passages.

That is worth being precise about, because the two halves fail differently:

| | symptom | fix |
|---|---|---|
| Retrieval failure | the right passage is not in `--show-only` output | chunk size, embedding model, k |
| Generation failure | the right passage *is* retrieved, and the answer still contradicts it | a larger generation model |

This one is squarely the second. `python ask.py --show-only` prints what was
retrieved without involving the model, which is the fastest way to tell them apart.
The fix is a bigger generator — `--model Qwen/Qwen2.5-7B-Instruct`, `--backend
ollama --model llama3`, or an API backend — and none of it touches the index. The
1.5B default is chosen so the project runs on a 16 GB laptop unattended, not
because it is the most accurate option.

This is also why the citations exist and why the UI puts the passages next to the
answer: a wrong answer whose sources are one click away is a wrong answer you can
catch.

See **[sample_questions.md](sample_questions.md)** for full worked examples —
generated by `python transcript.py`, so the documented answers are always answers
this pipeline really produced rather than hand-copied text that can drift.

## Choosing models

Generation has three interchangeable backends behind one interface, so the pipeline
runs whether or not you have a GPU, a daemon or an API key.

```bash
python ask.py "..."                                          # local transformers (default)
python ask.py --backend hf --model Qwen/Qwen2.5-7B-Instruct "..."
python ask.py --backend ollama --model llama3 "..."          # needs `ollama serve`
python ask.py --backend openai --model gpt-4o-mini "..."     # needs OPENAI_API_KEY
```

The default is `Qwen/Qwen2.5-1.5B-Instruct` — about 3 GB, runs at usable speed on an
M-series laptop, and follows the grounding instructions well enough to keep the
citations honest. A larger model gives noticeably better prose; it does not change
retrieval, which is where the accuracy actually comes from.

The embedding model is swappable too (`--embed-model`), but changing it requires
`python ingest.py --rebuild`, since vectors from different models are not
comparable.

## Files

| file | what it does |
|---|---|
| `get_data.py` | downloads the 10-paper demo corpus from arXiv |
| `rag/loaders.py` | PDF/txt → text, one record per page, whitespace repaired |
| `rag/chunking.py` | recursive overlapping splitter with stable chunk ids |
| `rag/embeddings.py` | sentence-transformers wrapper; handles query prefixes |
| `rag/store.py` | ChromaDB persistence, cosine search, per-source filtering |
| `rag/generate.py` | prompt construction + the hf / ollama / openai backends |
| `rag/pipeline.py` | `Assistant`: retrieve → diversify → generate → cite |
| `ingest.py` | CLI: build the index |
| `ask.py` | CLI: one-shot question or interactive REPL |
| `app.py` | Gradio web UI, showing passages beside the answer |
| `evaluate.py` | retrieval metrics + grounding checks |
| `transcript.py` | regenerates `sample_questions.md` from a real run |

## CLI reference

```bash
python ask.py -k 8 "..."                    # retrieve more passages
python ask.py --passages "..."              # print the retrieved text too
python ask.py --show-only "..."             # retrieval only, skips the LLM
python ask.py --source lora.pdf "..."       # search within one document
python ask.py                               # interactive REPL

python ingest.py --chunk-chars 800 --overlap-chars 150 --rebuild
python evaluate.py -k 10 --verbose
python app.py --share                       # temporary public link
```

## Notes

Everything under `data/` is generated — the PDFs come from `get_data.py`, the index
from `ingest.py` — so it is git-ignored rather than committed.

The demo PDFs are fetched from arXiv, which serves author-submitted preprints
openly; `get_data.py` identifies itself and spaces requests out as arXiv asks
automated clients to do. Copyright stays with the respective authors.
